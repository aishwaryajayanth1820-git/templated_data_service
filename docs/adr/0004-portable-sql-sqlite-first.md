# 0004. Portable SQL: SQLite first, PostgreSQL-compatible

- **Status:** Accepted
- **Date:** 2026-10-03
- **Deciders:** Aabel, Zypher
- **Affects:** `ddl` package, Flyway scripts, `ValueCodec`

## Context

The requirement says to develop locally on SQLite and later migrate to
PostgreSQL. `VIEW` and `DATA_SOURCE` rows may be inserted directly into the
database, bypassing the service.

## Decision

- Templates use logical types, which `SqlDialect` implementations
  (`SqliteDialect`, `PostgresDialect`) map to physical types.
- Enums are `CHECK (col IN (…))`, never PostgreSQL `ENUM` types.
- The primary key is a surrogate `id`: SQLite `INTEGER PRIMARY KEY
  AUTOINCREMENT`, PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- In SQLite, date and time values are ISO-8601 TEXT with a fixed format
  (`yyyy-MM-dd'T'HH:mm:ss.SSS'Z'` for datetime), so text order equals time order.
- Every constraint that can be expressed in SQL is emitted as DDL (NOT NULL,
  UNIQUE, FK, CHECK, including `requires`, `exclusive` and `atLeastOne` rules).
- System tables are migrated by Flyway with per-vendor folders
  (`db/migration/{vendor}`).

## Consequences

- Direct inserts can't break SQL-expressible constraints. App-only constraints
  (regex patterns, `expr` rules) are flagged in the UI instead.
- SQLite `decimal` is only exact to about 15 significant digits. Acceptable for
  development.
- Constraint changes on SQLite need a table rebuild
  ([0013](0013-schema-evolution-policy.md)).
